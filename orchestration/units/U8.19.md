**Bound:** ≤20 tool calls, zero LLM calls, no network, no graph build, ≤2 live `run`s (in-process, scratch

## Finding (measured, before the change) — the brief's suspicion was on the wrong side
Scratch pin copies against the **real** graph (`4790bbb1…897b`, 64 hex), in-process `_reuse_candidate`:

| pin len | matches | notices |
|---|---|---|
| 12 / 13 / 20 / 40 / 63 | yes | `PIN ABBREVIATED` + `REDUCED STRENGTH` |
| 64 | yes | none (correct) |
| **65 / 100** | **yes** | **none at all** |

Short pins already warned at *every* length. The real inconsistency: the condition was
`len(pin) < DIGEST_HEX`, so a pin **longer** than the digest matched on its first 64 characters with an
**unvalidated tail and no notice** — a policy with a threshold is not a policy.

## Decision
* **Rule (short pins):** a pin is reported whenever it supplies fewer hex characters than the full digest,
  at every such length — 63 hex is exactly as weak a control as 12.
* **Over-long: reject (a).** A sha256 is exactly 64 hex; a longer value is a corrupted/mis-edited pin, not
  an abbreviation. It is refused like malformed/unreadable/empty. (b) `validate-the-tail` would move the
  comparison U8.11 fixed; (c) accept-and-warn still lets a corrupt-tail pin "match" on a prefix.
* Implemented as two named predicates (`_pin_is_abbreviated`, `_pin_is_overlong`) used by both the run
  note and the shared line clause, so they can no longer disagree. `_same_digest` is untouched.
