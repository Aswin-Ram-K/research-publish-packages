# U5.33 — the snapshot rotation: correct the inherited claim, decide whether to pin it

## Card (as issued)
Two items about one accepted-but-consequential side effect of the render path:
`assemble()` **rotates** `ITEM.md.rN` snapshots in a bounded window and **appends**
to `HISTORY.md`.  Today that property lives only in a `#` comment, and the comment
carries an inherited imprecision ("banner files +1 per run").

* **Item 1** — measure the truth, then correct the comment (comment only).
* **Item 2** — decide whether the property deserves a machine-checkable pin; if
  pinned, prove the pin can fail by mutating a throwaway copy of the package.

## Item 2 — pin decision

**Pinned.**  Eviction is the *accepted* contract, not a defect awaiting repair:
`ITEM_SNAPSHOT_KEEP` exists to bound the one unbounded growth in a docket tree,
its max-index allocator is documented as load-bearing (first-free would delete the
*newest* prior revision), and the live `ITEM.md` always survives.  New node
`tests/test_docket_provenance.py::test_guard_u533_rotation_window_is_bounded_and_destructive`
(fills then exceeds the window): count ≤ `A.ITEM_SNAPSHOT_KEEP`; after overflow
exactly `KEEP` snapshots remain and the oldest index is the one that left, with one
index above the previous maximum arriving; `HISTORY.md` grows every render;
`MANIFEST.json` sha fixed after the first re-render.  Bound read from the constant
so re-tuning the window is not a failure; no literal `rN` is named.
