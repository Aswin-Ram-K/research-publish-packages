# Candidate tools — what they are and whether they add anything

Date: 2026-10-23. Author unit: S2 (web research).
Baseline compared against: `graphifyy==0.9.80` (Apache-2.0, pip) as measured locally — tree-sitter 0.25.x parsing 100+ code extensions (~20 bundled grammars), `networkx` graph (`graph.json`), Leiden clustering, CLI + `graphify-mcp` server (`query` with `--budget`, `affected` reverse traversal, `god-nodes`, `path`, `explain`, `update` hash-cached incremental, `watch`, `label`, `cluster-only`, `merge-graphs`, `diagnose`; MCP server exposes 10 tools + 6 resources), `.graphifyignore`, plus per-agent skill files shipped in the wheel (`skill-aider.md`, `skill-copilot.md`, `skill-agents.md`, …) and `graphify-mcp` as a console script. **Rule applied below: a candidate earns ADD only by naming something that command list cannot do.** Repo metadata below was pulled from the GitHub REST API on 2026-10-23 (stars/licence/last release are that snapshot, not a live claim); pages were fetched where a mechanism claim needed a quote.

## §0 Naming resolution

**"graphit" → adopted reading: Graphiti (Zep).** `getzep/graphiti` bills itself as "A Framework for Building Temporal Knowledge Graphs" — a Python framework for agent memory that stores entities/edges with validity intervals in a graph database, built for conversational facts, not for source files. Adopted because the spelling and pronunciation match exactly and it is by far the highest-profile project with that name (32.2k stars, Apache-2.0, v0.31.2 released 2026-10-20). Rejected: **Graphite** (`graphite.dev` — "Helps teams on GitHub deliver higher quality software, faster", i.e. PR stacking/review workflow; nothing to do with repo traversal) and **GraphRAG** (Microsoft's corpus-graph RAG, MIT, v3.3.0) with its family LightRAG / nano-graphrag / fast-graphrag — those are document-graph RAG systems whose *technique* (LLM entity extraction → Leiden communities → community summaries) is already the technique graphifyy implements over code. Link: <https://github.com/getzep/graphiti>, <https://graphite.dev/>, <https://github.com/microsoft/graphrag>.

**"gradft" → adopted reading: Graft, the repo "code map" that is now the Code map of Trail-Code.** The npm package `@nanonets/graft` (v0.24.1, MIT, first published 2026-07-15, binary `graft`) describes itself as "Build a repo's context graph as a folder of linked markdown files: a local, regenerable cache that every query keeps in sync with your code", and the upstream repo's README now labels that component "Code map (previously graft)". This is the only reading that matches "repo traversal": it produces markdown notes with exact `file:line` references plus a call-relationship graph, `graft init` / `graft build`, an `AGENTS.md` block, MCP config, and editor hooks that re-sync on edits. An independent write-up documents the same workflow (<https://kudithipudi.org/how-to-save-coding-agent-tokens-across-repos-with-graft/>). Rejected: GNU Guix "grafts" (package-rewriting mechanism; dominates naive search results, unrelated) and a Grafana product or Rust crate named Graft in this space — **unconfirmed**, no evidence found. Links: <https://www.npmjs.com/package/@nanonets/graft>, <https://github.com/trailhq/Trail-Code>.

## §2 Per-tool detail

**ast-grep (`sg`).** Parses each file with a tree-sitter grammar and matches *patterns written as code* — `$VAR` wildcards bind AST nodes, not text — so `sg -p 'await $CALL' -l python --json` returns file, byte range and line/column of the exact node. It adds what the baseline genuinely cannot do: graphifyy's artifact is a symbol/call graph queried by node identity (`path`, `explain`), never by syntactic shape, and greps in this pipeline do not exist at all. Cost/risk: search is read-only, but rewrite flags (`-U`/`--update-all`) write in place — run search-only against the target, and pass `--globs` rather than a shell `cd` into it. One static Rust binary, no runtime to install, no network. Language coverage is "whatever grammar is registered", which is the same constraint graphifyy already lives with.

**difftastic.** Parses both sides of a change with tree-sitter and diffs the syntax trees, so it can distinguish "syntactically identical, only reindented" from "a call target moved". It adds the one question the incremental path cannot answer today: `update` is hash-cached, so a touched file re-extracts — but nothing decides whether that file's *structure* changed or only its formatting, and `affected` needs a node set to walk backwards from a change that has not been mapped to nodes. Cost/risk: MIT/Rust, offline; it is a *diff display* tool, not a library API, so integration is a subprocess plus `--exit-code`; it has no cross-file/impact notion (that stays `affected`'s job).

**ripgrep.** The baseline has no text search in the pipeline at all — every claim-verification today has to go through the graph or through Python. `rg -n --json` gives byte offsets and line numbers, honours `.gitignore`, and is the cheapest possible "does this line still say what the docket claims?" check. Cost is effectively zero (one static binary, no config, no writes). Verdict is ADD on hygiene grounds rather than novelty: at 436 files it is microseconds, and at 100k lines it is still the right first tool for literal evidence.

**tree-sitter CLI.** The library is already a dependency (`tree-sitter>=0.25,<0.26`), so the CLI's marginal value is `tree-sitter query` for authoring and debugging S-expression queries without writing a Python harness, plus grammar fetching/building. It does not add a capability the process cannot already reach in-process — which is exactly why it is EVALUATE and not ADD. Cost: a second toolchain (C compiler for grammars) that must match the already-pinned tree-sitter ABI; version skew between CLI grammars and the 0.25 runtime is a real failure mode.

**semgrep.** Same tree-sitter parsing family, but its product is a rule DSL with limited dataflow and a huge curated rule registry; scanning is `semgrep --config p/x`. What it would add is intra-file/inter-procedural taint reasoning ("can this request parameter reach this sink"), which is not what "read-only repo → claims with file:line provenance" needs. Cost: LGPL-2.1 engine is fine for CLI use, but the interesting rules live behind the commercial platform (<https://semgrep.dev/docs/licensing>), and the Python+OCaml install is heavier than one `sg` binary for strictly less provenance precision.

**CodeQL.** Builds a relational database from a compiled/compilable codebase, then answers QL queries over it; the depth is real (dataflow, path queries). The licence is the blocker: the query repo is MIT, but the CLI ships under the "GitHub CodeQL Terms and Conditions" (<https://github.com/github/codeql-cli-binaries/blob/main/LICENSE.md>), and the database build is minutes-to-hours per commit — unusable as an incremental gate on a read-only Python target. Rejected on cost + licence, not on quality.

**Joern.** Generates a code property graph (AST + CFG + PDG in one schema) via `joern-parse`, then runs CPGQL/overflowdb queries — the strongest open (Apache-2.0) option for "does data flow from A to B". It is also a second graph model, a JVM service and an import step on top of `graph.json`, with Scala tooling in the loop. At 436 files the value is speculative; the cost is a JVM to operate and a schema to keep in sync.

**zoekt / Sourcegraph / Sourcebot.** Zoekt is a trigram-index text search engine (Apache-2.0, Go, Sourcegraph's maintained fork since 2017) that answers substring/regex queries far faster than scanning, at the price of a daemon and shard index. Sourcegraph wraps that with symbol services and SCIP indexes but now requires a licence key on Enterprise plans (<https://sourcegraph.com/docs/admin/licensing>) and its main repository is not publicly retrievable (API 404 on 2026-10-23). Sourcebot is the modern MIT self-hosted alternative but wants Node 24 + Docker Compose. All three solve "many repos, many users, one search box" — a problem this pipeline does not have.

**repomix / gitingest / code2prompt.** Each concatenates a repo (optionally with a tree, token counts, compression) into one prompt-shaped file. They overlap almost totally with the project's own context budgeting plus graphifyy's `file_slice.py`, and they make the failure mode worse: a flattened dump has no stable node identity, so a claim extracted from it still has to be re-located in the real file before it can carry `file:line` provenance. code2prompt has also not shipped since 2025-12-11.

**aider's repo-map.** The idea is "define a graph over symbol references, run PageRank seeded by the files in play, spend the token budget on the highest-ranked definitions". `query --budget` and `god-nodes` already do budgeted selection and centrality, so the marginal novelty is only the *seeding* rule (files currently in play) — an algorithm, not a dependency. Aider is an editing agent (Apache-2.0, last release 2025-08-09) and installing it to obtain a ranking function would be backwards; `networkx` is already a dependency and `pagerank` is one call. Overlap: near-total in function, partial in detail.

**Serena MCP.** Wraps per-language language servers behind MCP tools (`find_symbol`, `find_referencing_symbols`, edit/refactor), so references are *type-resolved* rather than tree-sitter-heuristic — the one genuine capability gap versus `graph.json`. Three costs stack: the app is GPL-3.0-or-later (`SolidLSP` is MIT), it needs a language server per language, and **this agent profile mounts no MCP client at all**, so nothing can call it today. EVALUATE only if mis-resolved cross-file edges start corrupting claims.

**code-graph-rag / potpie / blarify.** All three are the same pipeline as graphifyy — tree-sitter (or LSP) parse → graph → cluster/embed → query — with a database or LLM key attached. `code-graph-rag` needs Memgraph in Docker; `potpie` needs Neo4j plus LLM keys and indexes SDLC data the SQLite memory store already covers; `blarify` is a 234-star, release-less research artifact. None offers anything `graph.json` + Leiden does not, and each adds a service to operate.

**Understand / Sourcetrail.** Understand (SciTools) is commercial and proprietary, strongest at C/C++ cross-references and compliance reporting, and now ships an MCP agent — irrelevant to a Python/POSIX pipeline that must never write. Sourcetrail was archived in December 2021 (GPL-3.0, C++/Qt): dead, and its UI model was per-language indexers, not an agent-queryable graph.

**Graphiti.** Temporal knowledge graph for agent memory: entities/edges carry validity intervals, so "what did we believe at time T" is answerable; it runs on Neo4j or FalkorDB. Genuinely different from `graph.json` — but the domain is conversation, not source. The project's memory store is SQLite and already bounded; adopting Graphiti means a graph server plus LLM extraction calls per episode to store facts that a table stores adequately.

**GraphRAG family.** Microsoft's pipeline (LLM entity/relation extraction → Leiden communities → community summaries → global/local search) is the *same* structure graphifyy applies to code, minus the LLM-per-chunk cost, and its README now states the project is "largely in maintenance mode". LightRAG is the actively maintained variant (v1.5.7); `fast-graphrag` (last push 2025-11-01) and `nano-graphrag` (2026-01-27) are dormant. For code with a deterministic parser, paying an LLM to rediscover call edges that tree-sitter already resolves is a straight downgrade.

**Graft (Trail-Code code map).** The most interesting candidate on paper: `graft build` emits a `graft/` folder of linked markdown with exact `file:line` references plus a call graph, `graft init` wires an `AGENTS.md` block, a skill, MCP config and Claude Code session-start/edit/stop hooks, and queries re-sync against uncommitted edits (per <https://kudithipudi.org/how-to-save-coding-agent-tokens-across-repos-with-graft/>; the README now calls this component "Code map (previously graft)"). Its real novelty over graphifyy is the *artifact shape* — human-browsable markdown, federated parent index across sibling repos, hook-driven freshness. The blocker is structural, not technical: initialization and hooks write into the repository under analysis, and this workspace's hard constraint is that target repos are strictly read-only with no hooks installed inside them. Rejected for this pipeline; the borrowable idea is "emit a markdown view per subsystem" on top of `graph.json` without touching the target.

**SCIP.** A protobuf schema for symbols/occurrences plus one indexer per language (`scip-python`, `scip-typescript`, …), producing exact references from the compiler's own resolution. It is the cheap middle path between tree-sitter heuristics and a live LSP: build once per commit, read the index offline. Cost is a per-language indexer and a build step that must succeed on the target — at 436 Python files, probably not yet, at 100k lines, probably yes.

## §3 Category verdicts

**Repo traversal.** Nothing missing. `graph.json` plus `query --budget`, `affected`, `god-nodes`, `path` and `explain` already answer "what reaches what, and what does this touch" within a token budget; the only tool that packages traversal better for agents (Graft) does it by writing into the repo, which this workspace forbids. At 100k lines the pressure is not traversal but *seeding* — with 10× the nodes, a BFS that starts from the wrong node returns the wrong neighbourhood, and that is a ranking/entry-point problem (a few dozen lines over `networkx`), not a new tool.

**Code graph.** Near-total overlap across the whole field: every serious tool (code-graph-rag, potpie, blarify, GraphRAG, Sourcegraph) is parse → graph → cluster/query, which is exactly graphifyy 0.9.80. The single real gap is *resolution fidelity* — tree-sitter name matching guesses at cross-file edges that a type checker resolves exactly. At 436 files the guessing is adequate; at 100k lines it compounds into wrong `path` answers, and then SCIP indexes (or Serena if an MCP client is mounted) become worth their cost.

**Structural search.** Genuinely absent — no grep, no AST pattern matching anywhere in the pipeline today. `ast-grep` is the smallest possible fix (one MIT Rust binary, JSON spans, read-only by default) and is the clearest ADD in this report. Same answer at 100k lines; it is the *only* candidate that gets cheaper per unit of value as the repo grows.

**Structural diff.** Absent. `difftastic` converts "did this commit change semantics?" from a heuristic (file touched ⇒ re-extract) into a parse-level comparison, which is precisely the trigger the incremental refresh path needs. Small, MIT, offline. At 100k lines the payoff grows because re-extraction cost grows while formatting-only commits do not.

**Context packing.** Covered. The project already budgets context and slices by graph node; repomix/gitingest/code2prompt produce prompt blobs that lose node identity and therefore cannot carry `file:line` provenance forward. At 100k lines the answer is unchanged — packing must be *selection*, and selection needs the graph, not a concatenator.

**Code-search server.** Not needed at 436 files: `ripgrep` answers literal queries in milliseconds with no daemon. At 100k lines ripgrep still wins for a single-tenant pipeline; zoekt/Sourcebot/Sourcegraph only pay off with many repos, many users, or a persistent index that must survive restarts — and Sourcegraph now needs an enterprise licence key. Revisit only if the acceptance surface becomes multi-repo search-as-a-service.
