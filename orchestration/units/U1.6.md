## Purpose

A sibling unit (`U7.1`, the refresh engine) hit two defects in
`src/resextract/kg/graphify.py`:

> "Graphify.update emits `--graph` which `graphify update` rejects (exit 2) and it
> does not wrap the child in stdbuf, so `review._run_graphify_update` spawns stdbuf itself."

1. **`update()` built an argv the real CLI refuses** — `graphify update <path> --graph <file>`
   exits **2** with `error: unknown update option: --graph`, because 0.9.80's `update`
   accepts only `--force` and `--no-cluster`.
2. **No consistent line buffering** — graphify block-buffers stdout off-TTY, so a timeout
   silently discards all progress.

And then the class guard: *every flag the wrapper emits must exist in the real tool's help text.*

## 1. `update()` fix

* `--graph` is **never** built. `update(path, *, force, no_cluster, graph=None)` now assembles
  `["update", str(path), "--force"?, "--no-cluster"?]` via the pure `build_argv()`.
* `graph=` is kept for backward compatibility only: passing the **implied** default
  `<path>/graphify-out/graph.json` is a no-op, passing anything else raises the new typed
  `UnsupportedGraphTarget(GraphifyError)` naming the implied path and listing the subcommands
  that *do* accept `--graph`.
* Before/after, live:

```
old shape : graphify update <path> --graph <path>/graphify-out/graph.json
            exit 2 · stderr: error: unknown update option: --graph
new shape : ["update", "state/kg-update-test/duval", "--force", "--no-cluster"]
            exit 0
```

## 2. Line buffering, once, in the shared runner

* `Graphify.spawn_argv_for(argv)` prefixes **`stdbuf -oL -eL`**; `run()` calls it for every
  method, so there is exactly one place that decides buffering.
* `CommandResult.spawn_argv` is the argv the runner actually receives; `CommandResult.argv`
  deliberately stays the logical `graphify` command, because `tests/test_kg_graphify.py`
  indexes `argv[0]/argv[1]` and must not be regressed (task said: do not touch that file).
* `PYTHONUNBUFFERED=1` is set on the child as well — `stdbuf` only reaches C stdio, while a
  Python console script's own `TextIOWrapper` block-buffers off-TTY. Together they genuinely
  line-buffer.
* Opt-out: `Graphify(line_buffer=False)` or `run(..., line_buffer=False)`.
* Missing `stdbuf` → fail soft: child spawns unprefixed, `Graphify.notes` records a warning.

## 3. The class guard

`tests/test_kg_graphify_flags.py` parses `state/logs/graphify-0.9.80-help.txt` into
`{subcommand -> {accepted long flags}}`, then obtains each method's argv from
`Graphify(binary=..., dry_run=True)` — the **same** builder a live call uses, spawning nothing —
and asserts every emitted long flag is in that subcommand's set. **All** violations are reported
together, naming method, flag and subcommand.

* styles handled: indented block (`--backend B`), `--backend=<name>`, inline `[--flag VALUE]`
  (all eight `export <kind>`s), two-word subcommands (`global add`, `hook install`,
  `diagnose multigraph`).
* `--no-viz` is asserted legal for `cluster-only` and illegal for `extract`/`update`;
  `--graph` legal for `cluster-only`/`query`/… and illegal for `update`.
* **cover: 28 subprocess-issuing wrapper methods / 35 invocations.**
* **red→green (pasted in the test docstring):** injecting `--definitely-not-a-flag` into
  `update()` fails with
  `method update() emits --definitely-not-a-flag which graphify 'update' does not accept`
  (`1 failed, 12 deselected`); reverting passes (`1 passed`). Also reproducible in-process by
  `test_guard_has_teeth_on_a_bogus_flag` and `test_no_viz_emitted_for_extract_would_be_caught`
  (both drive the guard with a synthetic argv and `deviations={}`).

## 4. Ambiguities recorded (never silently skipped)

The parser exposes `AMBIGUITIES`; the guard asserts it is non-empty. Highlighted in the handoff:

1. **`clone`** declares no flag block of its own (line 21); its `--branch` / `--out <dir>` are
   printed inside the *`merge-graphs`* block (lines 28–29). Resolved by explicit override
   (`clone += {branch, out}`) and removal (`merge-graphs -= {branch}`).
2. **`export <kind>`** documents flags inline in `[...]` on command/continuation lines
   (lines 124–135) rather than in a flag block; per-kind attribution is exact
   (`--no-viz`/`--node-limit` only for `export html`, `--dir` only for `export obsidian`,
   `--labels` for all but graphml/neo4j/falkordb).
3. **No command-independent global flags exist** in 0.9.80; `--graph` is re-declared per command
   and is deliberately absent from `update` — that absence *is* the defect.
4. `install --platform` / `uninstall --purge` are parsed but unreachable from the wrapper.
5. `merge-driver`, `prs`, `watch` document no flags.

## 5. Audit of the rest of the wrapper (requirement 4)

Machine-checked by `test_strict_audit_finds_only_the_documented_deviation`, which drives every
method **plus** an explicit `extract(no_viz=True)` probe:

* **`other_argv_defects`: none.** No other method emits a flag its subcommand rejects.
* The single exception is a **documented, deliberate deviation**: `extract()` still forwards
  `--no-viz` when the caller explicitly asks (`no_viz=True`), even though 0.9.80 lists `--no-viz`
  only under `cluster-only`. A previous unit made that opt-in and the card says not to regress it,
  so it lives in an explicit `KNOWN_DEVIATIONS` allowlist with a reason; the guard drives
  `extract()` with the default `no_viz=False` and two dedicated tests would fail if it ever
  became a default.
