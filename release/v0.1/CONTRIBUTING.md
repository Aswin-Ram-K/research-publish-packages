## Forks and published modifications: welcome, and lawful

You do not need permission to fork this project or to publish your own modified version of it.
The licence's **Changes and New Works License** grants you a copyright licence to make changes
and new works based on the software for any permitted purpose, and its **Distribution License**
grants you a copyright licence to distribute copies. Publishing your fork, for a permitted
(noncommercial) purpose, is therefore expressly allowed. Just carry the licence and the
`Required Notice:` line with it, as the licence's Notices section requires.

## What is accepted here: ideas only

**Only ideas are considered for integration into this project. Code contributions and patches are
not accepted and are not merged.**

You are welcome to tell the author about a bug, an approach, an algorithm or a technique you
found. If the author wants it, he reads it, understands it, and **writes the code himself**. No
contributor code enters the tree.

This is deliberate, and it is not a comment on anyone's work. Here is the reason, stated plainly:

> If the author copies contributed code verbatim into the project, that code arrives carrying the
> contributor's Noncommercial licence — and it then cannot lawfully be included in a paid
> commercial licence. The commercial tier would silently stop covering part of the codebase.

Copyright protects expression, not ideas. Copying **ideas, approaches, algorithms and techniques**
and writing an independent implementation is the whole basis of this policy.

Because no third-party code is received, **no contributor licence agreement (CLA) and no DCO are
required**. If the author ever decides to accept code, that question returns: relicensing a
project that contains third-party code requires a contributor agreement granting the right to
relicense.

## The hygiene rule for the author

1. **Integrate by re-implementation.** Never by copy-paste. Never merge contributor patches or
   pull requests. If a fork's change is wanted: read it, understand it, then write the code.
2. **Never accept a patch into the tree.** Not even a one-line fix, and not even with attribution —
   the licence travels with the expression.
3. **Keep the boundary provable.** Keep this policy stated, keep merges closed (branch protection
   / a policy of not accepting PRs), keep a record of where an idea came from and that the
   implementation was independent, and keep the commit history clean of contributor authorship on
   the changed lines.
4. **Say which policy is in force.** This file states it: *only ideas are integrated; code
   contributions are not accepted*.

## What to send instead of a patch

Send a description: what the problem is, and what approach you would take. That is an idea, and
ideas are the input this project accepts.
