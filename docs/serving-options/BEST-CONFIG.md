# BEST-CONFIG.md — the four optimised setups, one per cell of the 2 models × 2 engines matrix

**Unit:** `R2-OPT-SETS`. **Machine-readable twin:** [`state/config/best-config.json`](../../state/config/best-config.json),
regenerated by `tools/best_config_build.py` (rerun `--check` to re-derive and diff; it writes nothing).
**Supersedes** the deliverable `R2-OPT-LOOP` blocked on: it asked a question already answered — the four
setups are the literal **2 models × 2 engines**, not a menu.

These are the **substrate** `R2-PROMPT` runs its four prompt arms (P0/P1/P2/P3) on. The R/A/C/H arms are
not setups; they are prompt policies. No Round-1 config is promoted here as a fill-in: every number below
is re-derived from a rows file in this workspace, in the same pass that writes the JSON.

`unc/turn` is the mean over the rows selected in each setup's `evidence.selector`, computed as
`prompt_tokens − cached_tokens` per row. Hit is `Σcached / Σprompt`. "Naive-history arm" is arm `A` of the
same cell — a different prompt *policy*, shown only so the setup's number is not mistaken for a policy
effect; it is **not** a second setup.

**CI convention, and whether each interval excludes zero.** Every `CI on unc/turn` is the two-sided 95%
Student-t interval of the per-arm mean uncached tokens per turn (`SE = sd/√n`, `df = n−1`), computed by
`tools/ci_backfill.py`; each is the **A** (naive-history) arm of its own cell, which is the arm
`unc_naive_history` in the table already reports, so the interval brackets the number printed beside it.
O3's own script is not in this tree (`orchestration/handoffs/R2-OPT-SETS.json` records its CIs as a
one-off run), so the convention was **identified** from O3's numbers rather than copied from code: this
rule reproduces O3's `[1235.25, 1532.17]` to +0.21 / +2.29 tokens on a 148-token half-width, where the
normal convention misses by −2.79 / −0.30 and in the opposite direction. **All four intervals lie strictly
above zero** — every setup's uncached cost is distinguishable from zero — but that is not a separation
from its own baseline: the difference against the R arm is `[−90.8, +90.8]` (O1), `[−89.6, +89.6]` (O2)
and `[−140.3, +140.3]` (O4), all straddling zero, so no setup is distinguishable from its own
baseline arm at 95%. **No interval is degenerate** (no `lo == hi`); the narrowest relative width is O1's
±64.2 on 723.4 (±8.9%), the widest O4's ±99.2 on 2231.0 (±4.4%).

## 3. Two cautions a verifier should read before quoting §1

1. **O4's argv is not fully "optimised", and the JSON says so by carrying it verbatim.** `V1` was launched
   **with** `--speculative-config {"method":"mtp","num_speculative_tokens":1}`. On occamy that exact flag is
   what made vLLM fail (`RuntimeError: No Qwen3Next layer found in the model.layers` — `WIN-VLLM` V3
   attempt 1), and MOE-VLLM records "MTP removed" for its cell. On the dense 9B it **ran and served**; the
   rows are its measurement. The card asks O4 to use "same flags plus `--quantization modelopt_fp4`" with
   no MTP. **No on-disk measurement of the 9B on vLLM without MTP exists**, so stripping it would make the
   argv something nobody measured — the thing this card forbids. O4 is emitted as launched, with this gap
   named. Removing MTP is a new measurement, not an edit.
2. **O3's `grid_unit 48` is a gcd, not a page.** The cell's launch block is 2,096 and **0/66** hot values
   are multiples of it — and **0/264** on O4's 2,096-grid too. No paged-block law is claimed for either
   vLLM cell; the gcd is the smallest observed step and nothing more.

## 4. The reading the card asked for — engine vs model

**The engine, not the model, sets the per-turn bill, and the 2×2 says so with the optimised launches too.**

- **Same engine, two models (the SGLang column):** O1 **729.20** vs O2 **713.99** — a **15.21**-token gap,
  **2.1 %** of the SGLang mean, in the *dense* model's favour.
- **Same weights, two engines:** occamy-1.0 costs **1384.96 − 729.20 = 655.76** more tokens/turn on vLLM
  than on SGLang (**1.899×**); qwen3.5-9b costs **2230.78 − 713.99 = 1516.79** more (**3.125×**).
- **On one engine, the model matters as much as the engine does:** inside SGLang the two models are within
  **2.1 %**; inside vLLM the dense model pays **845.82 more** than the MoE (**1.611×**).
  That is the C63 interaction reproduced on the optimised launches: *under SGLang the model is nearly free,
  under vLLM it is not.*

**Sizing caveat, stated rather than buried:** the two vLLM numbers are measured at **different memory
fractions on the same GB10** (O3 at 0.34 with a 13.93 GiB KV cache; O4 at 0.15 with a 64,736-token KV
cache). The engine→model "interaction" above therefore mixes engine, available KV cache, and checkpoint.
The **engine main effect** (O1 vs O3 on identical weights and identical context) is clean; the
**interaction** is not, and is reported as measured, not attributed.

## 6. Reproduce

```bash
.venv/bin/python tools/best_config_build.py            # write best-config.json
.venv/bin/python tools/best_config_build.py --check    # re-derive + diff, no write
```

`config_sha256` is `sha256(canonical JSON of argv)` — `json.dumps(argv, sort_keys=True,
separators=(',',':'))` — computed by the builder from the argv it emits, never copied from a log.

`R2-PROMPT` may read all four entries. **Two of them (`O2`, `O4`) are not byte-reproducible right now**:
their containers were torn down after the cell (`:8017` has no listener; O4's `wv-v1` was removed on
restore), so re-creating them means a launch, not a config edit. `O1` is already live on `:8012`.
