- **Can write:** `store.py::connect` (`PRAGMA journal_mode=WAL`, all the INSERTs)
  and the pipeline in `run.py`. The dashboard's own POST control routes
  (`app.py:235` rescan, `:255` doctor) only call read-only layer methods.
- **Concurrent writes are normal:** readers and writers share the store by design

- **Reproduced side effect (on the real store, boundary `_connect`):** a

## 2. Decision — option (d), a documented non-fix. `immutable=1` is NOT safe here.
Measured on throwaway copies (`tests/test_cli.py::test_immutable_uri_would_silently_lose_committed_wal_rows`):

| open | rows seen (1000 committed, in the `-wal`) | sidecars created |
|---|---|---|
| `mode=ro` | **1000** (correct) | `-shm` (and `-wal` if absent) |
| `mode=ro&immutable=1` | **`no such table: t`** — the WAL is never read | none |
| `mode=ro&nolock=1` | `unable to open database file` | none |

`immutable=1` asserts the file can never change; it therefore ignores the `-wal`
and answers with an empty database, *silently losing committed rows*, and it
disables the change detection that would notice a checkpoint rewriting the file
under the reader — trading file clutter for silent data corruption. It is safe
only for a store that is provably never written; this store is written by the
pipeline while a dashboard can be up, so **it is not safe here and is not used**.
`nolock=1` cannot open the file at all. Hence: keep `mode=ro`, document the
sidecars as the cost of a correct WAL read, and hand the real remedy up.
**Gives up:** nothing correctness-wise; the two sidecars remain, and they are not
evidence that the store was written (option (d) is explicitly not harmless for
*containment claims*, so the non-fix is recorded rather than shrugged off).

Boundary hardening applied while there: the non-URI fallback in `_connect`
(`api.py:451`) used to be a plain **read-WRITE** open, so a layer contracted to be
read-only could silently regain write access. It now carries
`PRAGMA query_only=ON`, making "read-only" true on every path.

## 3. Item 2 — the two unisolated CLI sites, made deterministic
Mechanism: **module-scoped autouse `RESEXTRACT_STATE_DB` env redirect** to a byte
copy (`shutil.copyfile`, so the fixture itself never opens the real store) — the
pattern U6.17 proved in `tests/test_dashboard_auth.py`. It **covers every
construction in the file** (the two `create_app(dockets_dir=…)` sites at the old
`:343`/`:419`, the `create_app(host="0.0.0.0")` refusal call, and any site added
later), which an explicit `store_path=` at the two known sites would have missed.
The prior env value is restored in teardown, so nothing leaks into another file.
Isolation is asserted on the **observable resolved path**:
`app.state.dashboard["store_source"] == "env"`, `["store_path"]`,
`["store_resolution"]["store_path"]`, `DataLayer.resolution()["store_path"]`, and
`!= REAL_STORE.resolve()`.

## 5. Hand-up
Changing the store to `journal_mode=DELETE` **would** remove reader sidecars
entirely (`run.py` already does exactly this for its run-scoped copies and
documents the rationale). It costs the WAL's concurrent reader/writer capability
(writers take an exclusive lock per write), so it is a *writer-side* decision for
`store.py`/`run.py`, not something a read-only reader unit can apply. Recommend a
dedicated unit own that change plus a concurrency test.
Other callers still opening without isolation (named, **not** fixed):
`src/resextract/cli.py::serve`, `src/resextract/dashboard/__main__.py::main`,
`src/resextract/dashboard/app.py::create_app` (all default `store_path=None`).
Also present: an untracked stray `src/resextract/dashboard/api.py.V6C-backup-B2`
(not created by U6.18).
