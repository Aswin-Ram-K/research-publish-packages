# encoder-crossover-190 — released data and verification tooling

## What this is

This is the **released data and verification tooling** for the paper

> *The small-encoder crossover is a prompted-baseline artefact: a fine-tuned encoder head loses to a
> fine-tuned 4B decision model by 0.33 and to a majority-class control*

by **Aswin Ram Kalugasala Moorthy** (2026). It is the deposit-level front matter for the archive; the
per-directory detail lives in `README.md`, `MANIFEST.json` and `results/REPORT.md`.

## What this is not

- **The harness is withheld.** There is no `harness/` directory. The collection, preparation, training,
  evaluation, analysis and linting code that produced the accuracies in `results/` is deliberately not
  distributed, nor are any model weights (the three arms are public Hugging Face checkpoints fetched at
  run time).
- **The checks here do not retrain or re-render anything.** They re-derive the published numbers
  **from the stored records** in this package. They read bytes that ship with the deposit; they do not
  regenerate a model input, run an arm, or re-run the evaluation pipeline.
- **This is not a reproduction package.** A reader cannot retrain an arm, cannot reconstruct the model
  inputs, and cannot re-run the measurement from this deposit alone. What is verifiable here is that the
  shipped records are internally consistent with the published numbers.
- **This is not the paper text.** The paper manuscript is a separate work under **CC BY 4.0**.

## How to use it — the exact checks and their expected output

Standard-library-only Python 3; no third-party dependencies, no network, no GPU. Run each command from
the top of the extracted directory (the directory holding `verify/`).

### 1. Re-derive the claims

```bash
python3 verify/recompute-claims.py
```

Expected: **exit status `0`**. The tail of the output reads

```
  ALL PUBLISHED NUMBERS REPRODUCED: True
  VERDICT: PASS
  fixture correctness digest: c7696edc0e71d83faafc2e489925788e0f36c6af94913674f8953718352c9a55
```

before that it prints the five hand-set arms (`modernbert-base` 0.347368, `deberta-v3-base` 0.347368,
`setfit-mpnet` 0.263158, `majority-class` 0.452632, `shuffled-label` 0.231579), the `decider-4b-repro`
arm at 0.678947, the paired McNemar 2x2 (`both=39 headOnly=27 deciderOnly=90 neither=34`, exact
`p = 4.166818e-09`) and the second-labeller kappas. Any non-zero exit names the claim that failed.

**One value is not recomputable here and the script says so:** the `0.6684 decider-4b published
baseline` is printed as a `QUOTED CONSTANT (results/REPORT.md 2; not recomputable in this subset)`. It is
compared, not re-derived. The harness that would re-derive it is withheld. This is a known boundary of
the release, not a failure.

### 2. Re-parse the decision instrument

```bash
python3 second-labeller/parse_fixture.py
```

Expected: **exit status `0`** and a JSON summary containing, among other keys,

```
"records_found": 190,
"cases_parsed": 190,
"parse_failures": [],
"options_total": 721,
"single_option_cases": [],
"duplicate_ids": []
```

`parse_failures`, `single_option_cases`, `duplicate_ids`, `answer_outside_option_set` and
`bad_option_arity` must all be empty.

### 3. Re-compute the inter-labeller agreement

```bash
python3 second-labeller/compare.py
```

Expected: **exit status `0`** and a JSON report whose headline values are

```
"routeA":  { "kappa": 0.3248813212427869, "agreement": 0.34210526315789475, "ties": 141 }
"routeB_primary": { "kappa": 0.9013584840356494, "agreement": 0.9052631578947369, "n_disagreements": 18,
                    "AB_mutual_agreement": 0.3684210526315789 }
"closed_subset":   { "kappa": 0.8837023738280471, "n": 106 }
"roster_and_bespoke_subset": { "kappa": 0.9139973672663448, "n": 84 }
```

Steps 2 and 3 regenerate `second-labeller/cases.json`, `blinded_cases.json`, `parse_summary.json`,
`disagreements.jsonl` and `metrics.json` **from** `fixture/fixture-190.json`. On an unmodified tree the
regenerated bytes are identical to the shipped ones, so the tree's sha256s do not move; if you want to
be sure, copy the directory first and diff afterwards.

## Integrity — what `MANIFEST.json` covers, and what it does not

**Package content vs deposit metadata.** The released *package* is **29 files**. The deposit *archive*
wraps that package in a single top-level directory and adds exactly **2 deposit-metadata files** on top
of it — `CITATION.cff` (the deposit-level citation) and this file, `README_DEPOSIT.md`. The archive
therefore ships **31 files**. Those two files are the **only** files in the archive that are not package
content; every one of the other 29 is byte-identical to the package. `README.md` is the package's own
README and ships unchanged; `README_DEPOSIT.md` and `CITATION.cff` were added on top of it for the
deposit.

**The two trees carry two different manifests under the same name.** They are the same file name
because each is the manifest of the tree it sits in:

| tree | `MANIFEST.json` describes | `files[]` entries | `counts.files` | self-exempt |
|---|---|---|---|---|
| the package tree (author-side; not shipped) | the package — its own 29 files | 28 | 29 | itself (`manifest_self`) |
| extracted archive root (the archive) | the archive — its own 31 files | 30 | 31 | itself (`manifest_self`) |

So the archive's manifest enumerates **30** entries: the 28 package entries plus `CITATION.cff` and
`README_DEPOSIT.md`. It does **not** enumerate itself — a self-referential sha256 is impossible — and it
carries its own digest in `manifest_self`; `counts.files` includes it, `counts.bytes_total` excludes its
own bytes. That is the same self-exemption convention the package manifest uses.

Both copies are fail-closed over the files on disk **in the tree that ships them**. The archive's copy
is the package's copy *regenerated after the archive tree is assembled* (see "How the archive is
assembled" below) — regenerating it inside the package would make it false of the archive, and
regenerating it only in a staging tree that is not shipped makes it false of both.

### The package's manifest (28 of 29, itself exempt; author-side, not shipped)

The package tree does not ship; the author ran this at its top (which has no deposit
extras):

```bash
python3 - <<'PY'
import hashlib, json, os
m = json.load(open("MANIFEST.json"))
bad = []
for e in m["files"]:
    h = hashlib.sha256(open(e["path"], "rb").read()).hexdigest()
    if h != e["sha256"] or os.path.getsize(e["path"]) != e["bytes"]:
        bad.append(e["path"])
print("MANIFEST checked:", len(m["files"]), "files; mismatches:", bad or "none")
PY
```

Expected: `MANIFEST checked: 28 files; mismatches: none`.

### Check the archive's manifest (30 of 31, itself exempt)

Run this at the top of the **extracted archive** (which has the two deposit extras):

```bash
python3 - <<'PY'
import hashlib, json, os
m = json.load(open("MANIFEST.json"))
bad = []
for e in m["files"]:

print("MANIFEST checked:", len(m["files"]), "files; mismatches:", bad or "none")
```

Expected: `MANIFEST checked: 30 files; mismatches: none`.

### Independent checker (author-side; not shipped)

The author's independent checker re-hashes every listed path and walks the tree for files the manifest
omitted. It exits non-zero if any of `missing`, `hash_mismatch`, `size_mismatch`, `unlisted`,
`listed_but_absent` is non-zero. That checker is author-side build tooling and **does not ship** with the
deposit, so it cannot be run from the archive; the inline `MANIFEST.json` re-hash above is the shipped
equivalent for a reader.

The author ran it at the top of the **extracted archive**, which reported
`missing=0 hash_mismatch=0 size_mismatch=0 unlisted=0 listed_but_absent=0`, then
`VERDICT PASS`, **exit `0`** — nothing in the archive is unlisted, deposit extras included. Run against
the package tree (author-side; not shipped), the same checker reported `VERDICT PASS`, **exit `0`**.

### How the archive is assembled (the ordering that makes this true)

The two source trees are the package tree (author-side; not shipped — 29 files, whose `MANIFEST.json` is what it is)
and the deposit extras. Because `MANIFEST.json` has the same name in both trees, the order is what
decides which files each copy describes:

1. Stage the package's 29 files into `<stage>/encoder-crossover-190-released/`.
2. Add the 2 deposit extras — `CITATION.cff` and `README_DEPOSIT.md` (this file) — to the stage.
3. **Regenerate `MANIFEST.json` in the stage**, with the project's manifest generator (`--package
   <stage>/encoder-crossover-190-released`, `--no-note` to match the shipped key set).
   It now describes 31 files.
4. Pack deterministically:
   `tar --format=gnu --sort=name --owner=0 --group=0 --numeric-owner --mtime=@0 -C <stage> -cf -
   encoder-crossover-190-released | gzip -n -9 > encoder-crossover-190-released.tar.gz`.

Step 3 after step 2 is the whole fix: the archive's manifest is generated from the archive's own tree,
after that tree exists. The package's own `MANIFEST.json` is never written by this step and keeps
describing the 29-file package.
