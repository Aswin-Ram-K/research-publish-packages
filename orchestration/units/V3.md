## Key findings

- **No assertion was deleted.** Search tests: 5 lines removed, of which exactly the two claimed
  `degraded is False` assertions, each replaced by three stronger assertions; plus a rename and the
  `degradation_evidence` tuple→attribute change. Fetch tests: 4 lines removed, **0 assertions** — one
  rename and three `check()` unpack sites in **two** tests widened to 3-tuples (exactly as claimed).
  Caveat: no git baseline exists for these tests, so the diff is against U3.3's own backups.
- **UNASSERTED (the highest-value finding):** a transport failure is not cached as a negative result —
  correct in code, but no test guards it. Also unasserted: HTTP 4xx/5xx → `ok=False`, empty/malformed
  body → `ok=False`, and "the latch survives a later success" (all verified correct by my probe).
- **Full red→green, 4/4, sha-proven** — and a real gotcha: a byte-length-neutral revert within the
  same second let Python serve a stale `.pyc`, producing a **false failure on the restored file**;
  re-run under `PYTHONDONTWRITEBYTECODE=1` + `__pycache__` purge. Guard (b) only.
- **Live search is not what U3.1 recorded.** `unresponsive_engines` was
  `[[brave,"Suspended: too many requests"],[duckduckgo,"CAPTCHA"],[qwant,"CAPTCHA"]]`, not `[]`; and
  dead empties also arrived at 59.7/126.2/340.0 ms — above `fast_empty_ms=50` — so latency is a lower
  bound on deadness, not a classifier. The `fast_empty` escalation itself did reproduce: 1.617 ms and
  1.315 ms, latching on the first call.
- **The live fetch claims all reproduce**, including the exact arXiv digest `0dde6e26…`, `page_date
  2025-05-29`, `changed=false`, 0 HTTP calls on a cache hit, and the stub's first bytes
  `"\n```\n404: Not Found\n```\n\n"` (a GitHub raw 404 body, 22 usable chars, `suspect=True`).
