# U4 — `compaction`: does forking avoid the compaction cache break?

**Status:** done · **Requests:** 454 live (438 batch + 3 smoke + 13 probe) · **Wall:** 257 s batch
**Verdict:** **REFUTED — the kill condition fired.** The fork policy does not avoid the break; it
is indistinguishable from `summarise_in_place`.

## Design

* Corpus generated in-cell (`u4_corpus.py`, seed 20261020, `u4_sessions.json`, payload sha256
  `78b725cbe281d55da29743f9ea1e7daa38d8345711a5759102c9c2e92e555d82`): 3 sessions × 44 turns,
  ~30.8k estimated tokens each. `corpora/compaction.json` does not exist, so the corpus is mine.
* Budget 8,000 estimated tokens, `keep_last=2` → 7 events/session for `summarise_in_place` and
  `fork`, 4 for `sliding_window` (it drops history, so it hits the budget later). 54 events total.
* One arm: `naive_append` (the shared renderer). Only the compaction policy varies.
* 3 additional no-compaction control cells (14 turns, budget 10⁹) as the append-only baseline.
* `volatile={}` on every turn, so the rendered prompt never changes for a non-cache reason.
* Cold isolation: per-cell salt via `make_salt`. `cached_tokens` read from
  `usage.prompt_tokens_details.cached_tokens`; **23 null coercions** counted, not swallowed.
* `reps=1` on purpose: a second repetition re-sends byte-identical post-compaction prompts the
  server has already cached, so it would measure memoisation, not the break.

## Result

`break_cost = uncached − (prompt_tokens mod 64)` at the first turn after each compaction event.

| policy | events | median | p25–p75 | total |
|---|---|---|---|---|
| `summarise_in_place` | 21 | 1792 | 1728–6016 | 63,296 |
| `fork` | 21 | 1792 | 1728–6016 | 63,232 |
| `sliding_window` | 12 | 1728 | 1728–1744 | 20,928 |

Paired, same session and same event: `fork − summarise_in_place` median **0**, 18/21 pairs exactly
0, max |Δ| **64** (one grid block), permutation p = **1.0**. `fork − sliding_window` median 64,
max 4416, p = 0.45.

**Fork breaks on 21/21 events, not once per fork.** The claim under test — "fork leaves the old
chain untouched, so the break happens once and the 64-grid resumes" — has no measurable support.

## Why (token positions)

The break is caused by *new bytes at message 0 of the body*, not by the word "rewrite". Both
policies put a different node at the front of the context, so the first request after the event
re-prefills everything behind it. The event-turn prompt is rewritten at ~99 % of its length for
`summarise_in_place` (structural replay: `rewritten_share_of_prompt` 0.9895) and the break equals
essentially the whole post-compaction prompt: median 6,165 tokens for summarise/fork vs 1,828 for
sliding. A pointer renderer would not change this: the fork point sits at the *front*, so however
short the pointer token is, the suffix behind it is uncached. Only the append-only control keeps
its reuse (78.6 % hit rate).

`sliding_window` is cheaper **per event** only because it drops the folded history: a 1.8k-token
prompt that is entirely new costs less to re-prefill than a 6.2k one. Over the whole session it is
the *most* expensive policy — 293,901 uncached tokens vs 256,883 for `summarise_in_place`
(hit rate 0.592 vs 0.730) — because its window re-anchors near the front on every turn, so reuse is
lost continuously and not just at events. The cheapest policy over a 44-turn session is
`summarise_in_place`.

## Instrument finding (must not be lost)

The brief's append baseline `cached == 64*floor(len/64)` **does not hold on this server**:
372/372 warm-append rows deviate, residual histogram 896×103, 1792×71, 1728×62, 2624×52,
3520×31, 832×18, 2688×17, 3584×7, 6976×3; a dedicated 6-turn pure-append probe reproduced it
(`u4_grid_probe_append.json`: 935→0, 1804→896, 2643→896, 3529→2624, 4418→2624, 5284→2624).
The KV pool is *not* the cause (U2's `server_config.json`: 1,306,681 tokens, `page_size=1`,
`max_mamba_cache_size=64`); it is the hybrid mamba radix cache's checkpoint behaviour. Consequence:
`break_cost` as specified is a valid *relative* comparison between policies on the same turns, but
its absolute value should not be read as "tokens the break cost beyond a clean append" — the
ambient append residual on this box is already 0.9–2.7k tokens.

## Caveat that does not rescue the claim

The shared renderer was changed by another unit at 18:07:16 (`NAIVE_APPEND` now emits every
non-invariant node verbatim, including the fork head), so `fork` and `summarise_in_place` render to
prompts 1–2 tokens apart. That is *why* the two are identical — but it also means a real
pointer-rendering fork still breaks at the front of the context, which is exactly where the cost is.
The refutation is therefore about the mechanism, not just about this renderer.
