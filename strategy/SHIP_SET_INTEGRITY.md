| field | before (inherited) | now |
|---|---|---|
| manifest sha256 | `0553ea51…c993d8c` | `f3e4a22c…1fc614` |
| `counts.files` | 42 | **45** (the real file count) |

| `counts.hashes_verified_identical` | 14 | 1 (recomputed as `sha256 == source_sha256`) |
| `counts.derived_excerpts` | 2 | 2 |

**Self-reference decision (deliberate).** The manifest does **not** list itself — a self-referential sha256
cannot be self-consistent. This is the workspace convention already recorded in the inherited
`manifest_self` field, so the convention is kept and the field now says exactly what is true:
`MANIFEST.json` is the only file in the tree absent from `files[]`, and `counts.files` / `counts.bytes_total`
count it. The manifest was solved to a **fixed point** in which `bytes_total` includes its own final byte
size (2,986,505 bytes across the other 44 files + 21,873 bytes of manifest = 3,008,378).

**Schema and provenance preserved.** Key names are unchanged and no field was invented. `source`,
`source_sha256` and `kind` are carried over verbatim for the files the old manifest described; entries added
by this regeneration carry **no** `source_sha256`, because no source digest was established for them (no
digest was invented). `identical_to_source` was recomputed mechanically as `sha256 == source_sha256`;
`region_verified_identical_to_source` is left as recorded (the excerpt-vs-source region cannot be
re-derived without the source). The original `generated_by`/`generated_utc` provenance and the old counts
are recorded in the preserved `amended_by` / `manifest_scope_note` strings.
