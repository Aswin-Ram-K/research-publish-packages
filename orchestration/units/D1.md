## Method
1. Three spaced `curl :8012` probes + `/dev/tcp` TCP check + ICMP.
2. Probed the other GX10 services (`:8000`, `:8013`, `:8010`, `:8090`, `:22`) to separate

4. Ran the inside-the-box probes — correct discriminator is the **LAN-bound** publish
   (`curl http://192.168.2.168:8012` from the box), not `127.0.0.1` (the publish is host-IP-only,

5. Timeline correlation via box uptime, workstation uptime.

## Result
**Diagnosis: `gpu_or_oom`** — owning unit `gx10-occamy-nvfp4.service`.

`:8012` is not merely down; the container is **crash-looping**. Every cycle SGLang loads the NVFP4
weights (~145 s) and then aborts in its own KV-cache sizing guard:

```
ValueError: Loaded weights leave no GPU memory for the KV cache under --mem-fraction-static=0.5.
Raise --mem-fraction-static above 0.500 (minimum viable = 1 - available/pre = 0.4993).
```

then `kill_process_tree` → `status=137`, `Restart=on-failure`/`RestartSec=20` → restart counter 1, 2, 3.
The "minimum viable" value **drifts upward** across cycles (0.4929 → 0.4993) against a configured
`0.500` — a margin of 0.0007. That is why it was green earlier and dead now: a marginal unified-memory
regression on the GB10 UMA part (where the unit's own comment notes `cudaMemGetInfo` under-reports),
not a config change and not a reboot (box up 35 days, workstation up 29).

Restore command (a human's call, **NOT executed**):
`systemctl --user restart gx10-occamy-nvfp4.service`
Durable fix: raise `--mem-fraction-static` from `0.50` to ~`0.60` in that unit's `ExecStart`.

Full verbatim evidence: `state/logs/D1-occamy-diagnosis.log`.
