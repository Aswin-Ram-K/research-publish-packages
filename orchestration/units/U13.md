## Design decision

The defect is in the **library**, not the cell. `render.py` was already right *given*
a chain whose fork node says something a summary node does not — but `compact(FORK)`
put only the summariser's output in the fork node's text, so the chain itself carried
no distinction. The only renderer-level distinction (`POINTER_FORK`'s header label)
exists in one policy and is 93 chars of preamble; a cell-only fix (render the fork
cell with `POINTER_FORK`) would change the prompt for one arm only, confounding the
renderer with the compaction policy U4 deliberately holds fixed.

So the smallest change is one marker line in `compact`'s FORK branch: the fork root's
text becomes

```
[fork] replaces head through <last folded head node_id>; forked_from <pre-compaction chain_hash>

<summary text>
```

Both addresses are already sha256 content addresses, so the fork node's own id commits
to exactly which prefix it replaced. `SUMMARISE_IN_PLACE` still rewrites the head
silently, with no pointer. Because the marker lives in `node.text`, it reaches the
prompt under **every** renderer (append-only arms emit every non-invariant node), so
U4's single-renderer design becomes genuinely comparative without editing the cell —
and U4's historical rows are not silently mismatched by a code change.

Cost: +175 JSON chars (~44 estimated tokens) on the fork prompt of an 8,343-token
event — 0.5%, and it is real provenance, not padding. `equal_information` (POINTER vs
NAIVE_APPEND over the same chain) still holds in both arms; what differs is between
arms, which is the point.
