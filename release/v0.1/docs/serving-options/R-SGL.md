**Unit:** R-SGL (literature/config survey — **no experiments run**, 0 live model requests, no `.occamy.lock`).
**Subject deployment:** SGLang on one GB10-class GX10 node, Qwen3.5-MoE hybrid-attention, `max_model_len=131072`.
Live config: `page_size=1`, `disable_radix_cache=false`, `radix_eviction_policy=lru`, `chunked_prefill_size=8192`,
`max_total_num_tokens=1306681`, `enable_hierarchical_cache=false`, `hicache_storage_backend=null`,
`enable_lmcache=false`, `enable_session_radix_cache=false`, `uses_mamba_radix_cache=true`,
`mamba_radix_cache_strategy=extra_buffer`, `max_mamba_cache_size=64`.
**Observed on that box:** cache hits land on a 64-token grid; `cached = 64*floor((L-1)/64)`; a prompt whose length
is an exact multiple of 64 misses on the first immediate repeat and hits on the second.

**Headline finding.** With `page_size=1` the full-attention KV component is token-granular, so the 64-token grid
cannot come from paging. It comes from the **MAMBA/GDN checkpoint granularity**: `FLA_CHUNK_SIZE` is 64, and under
`extra_buffer` the recurrent state is handed to the radix tree every `--mamba-track-interval` tokens (published
Qwen3.8 recipes use 64). The unified radix match boundary is the deepest node accepted by **all** component
validators, so a token-granular KV match is floored to the mamba checkpoint grid → `64*floor((L-1)/64)`.
The "miss once, hit twice" behaviour is *consistent with* commit-at-fold-time but commit timing is **not documented**;
treat it as a hypothesis, not an established fact. Note also that the SGLang cookbook pairs `extra_buffer` **with
`--page-size 64`**, while our box runs `extra_buffer` + `page_size=1` — an undocumented combination worth isolating.

## What a reviewer would demand we test, in priority order

1. **`--page-size 1` vs `64`, with `extra_buffer` held fixed.** This is the direct lever on the 64-token grid we
   actually measured, and our combination (`extra_buffer` + `page_size=1`) is the one the cookbook does *not*
   document (it documents `extra_buffer` + `--page-size 64`). Sweep both, report matched-prefix length, hit rate and
   TTFT at fixed prompt lengths on and off the 64 grid. Until this is run, the grid's cause is a hypothesis.
2. **Cache telemetry before any optimisation** (`--enable-cache-report` / `--enable-metrics`). Every published
   number above is a hit-rate or TTFT delta; we cannot claim any of them without first measuring our own baseline
   hit rate and eviction behaviour on this box.
3. **Radix eviction policy** (`lru` → `slru` / `lfu` / `priority`, then `tlru` under the unified tree). Cheapest
   restart-only lever, no correctness risk, and the "hit count not incremented for chunked-prefill steps" caveat
   is exactly the kind of thing that only shows up in a measurement.
4. **HiCache L2 on/off** (`--enable-hierarchical-cache --hicache-ratio 2`), given the 6× / −80% TTFT published
   claim. Must include a memory check first: this box's unified memory and the `mem-fraction-static 0.50` crash-loop
   history make the host-DRAM tier the highest-risk change on the list.
5. **MTP / NEXTN** (`--speculative-algorithm NEXTN --speculative-num-steps 3 --speculative-eagle-topk 1
   --speculative-num-draft-tokens 4`, `--enable-linear-replayssm-spec`), the only lever with a same-family measured
   claim (+10% throughput, 2.33× per-user on Qwen3.8). Gate it on two checks: does *this* checkpoint ship MTP
   weights, and what is `--max-running-requests` (NEXTN silently caps it at 48).
6. **`--chunked-prefill-size` × `--linear-attn-prefill-backend`** (4096 / 8192 / 16384). Our 8192 is exactly at
   the FlashInfer GDN prefill auto-selection boundary; a reviewer will ask whether the fast path is actually on.
7. **Session radix cache / unified radix tree** for multi-turn agentic traffic (2.9%–16.6% TTFT claim). Only worth
   running if our workload has real multi-turn sessions; it is the natural pairing with `session_id` accounting.
8. **HiCache L3 file backend via runtime attach/detach** — the one cache feature that can be turned on **without a
   restart** on this box, so it is the only lever testable inside a frozen-server run.
9. **Out of scope on one node, recorded as such:** cache-aware routing (needs ≥2 workers) and PD disaggregation
   (needs ≥2 processes/GPUs). Their published gains are the largest in this table (+92% throughput / 20%→75% hit
   rate; 84% TTFT reduction), which is the argument for eventually testing them on a multi-node setup — not on the
   GX10.

**Evidence discipline:** every row above is documentation or a vendor/team benchmark from a primary source; none of
it was reproduced here. Rows 9, 13, 18 and 19 carry no measured claim and are marked as such rather than estimated.
