**Status:** done — author measurement. A different unit verifies.

**Answer.** Nothing in R's *rendered window* is rewritten between compactions: on all
37 steady turns the message prefix is byte-identical to the previous turn's, the
invariant-head hash is one value across all 40 turns, and the summary-node hash changes
only at the two fold turns. The ~1,660 tokens/turn is nevertheless ~70 % *previously sent*
tokens, and it is the **tail** of the window: the endpoint reuses only a prefix that ends
at an **earlier turn's prompt end**, skipping the newest 0–3 appended messages (lag 1–2
turns before the first fold, 3–4 turns after it), quantized to the 64-token page. The
summary node is cached, never re-prefilled; the 64-grid sets the granularity, not the cut.

## Purpose (one)

Settle **G6**: U15's R arm (`summarise_in_place`) re-prefills ~1,660 tokens/turn between
compactions although the prompt averages 5,812 tokens and the summary node is constant,
and F's turns 36–40 advantage (4,595 vs 9,011 uncached) is reported without a mechanism.
Instrument R (priority) and F, attribute the re-prefilled span to the window's tail, the
summary node, or cache chunking.

## Design (copied from U15; one deviation)

Corpus `corpora/endtoend.json` scenario `E1`, turns 1–40; `needs_compaction` at 8,192 est
tokens; compaction points **18 and 35** derived once offline from the reference arm;
`keep_last=2`; renderer `NAIVE_APPEND`; deterministic offline stub summariser (750 chars);
`max_tokens=4`, `thinking=False`, `stream=True`; one request in flight; lock held for the
whole batch.

**Deviation (assumption):** fresh salts `make_salt(2501)` (R) and `make_salt(2502)` /
`make_salt(2503)` (F, F2) instead of U15's 1501/1502, so the batch starts cold even if the
endpoint still held U15's prefixes. The salt is a constant 16-hex-char token in message 0;
prompt counts track U15's within 1–3 tokens.

## Instrument (per turn)

Rendered window at message level — node id, kind, role, chars, estimated tokens,
cumulative estimate, content sha256 — plus the message diff against the previous turn
(carried / new / dropped ids, changed message indices, `prefix_identical`), invariant-head
sha256, summary-node sha256s, `prompt_tokens`, `cached_tokens`, `prompt_tokens % 64`,
`delta_prompt_tokens`, delta rendered bytes.

## Decomposition (additive, closed, tolerance 0)

For a steady turn whose prefix is **verified** byte-identical:

```
uncached_t = new_tail_t + (prompt_{t-1} % 64) + re_prefill_t + residual_t
new_tail  = prompt_t - prompt_{t-1}            (the appended message)
boundary  = prompt_{t-1} % 64                  (64-grid tail)
re_prefill= floor64(prompt_{t-1}) - cached_t   (previously sent, not cached)
residual  = 0 on every steady turn of both arms
```

The head-rewrite component is measured, not assumed: 0 changed messages on 37/37 R
steady turns.

Attribution of the 1,659 post-fold tokens: **98.2 % tail** (new node 27.5 % + re-prefilled

Evidence that the re-prefilled span is the tail:

- 33/37 steady turns: `cached_t` equals `floor64(prompt_j)` for an **earlier turn** j (lag
  histogram 1:7, 2:8, 3:10, 4:8); the four exceptions are exactly the two post-break
  recovery turns after each fold (t19, t20, t36, t37).
- For every one of those 33, `re_prefill` equals the token sum of the skipped trailing
  messages within 128 tokens (0 exceptions), i.e. the span is an **integer number of
  appended messages**, not an arbitrary token range.
- All `re_prefill` values are multiples of 64 (0, 448, 512, 832, 896, 960, 1344, 1408,
  1600) — chunking sets granularity; the cut lands on a message boundary, so chunking does
  not choose the span.
- The summary node sits *before* the cut on 14 of the 16 post-fold steady turns (cached
  1,920 ≥ head 848 + summary 188), its hash is 11b8e9bc… for t18–34 and a1273293… for
  t35–40 (changed only at the folds), and the invariant head is one hash for all 40 turns.
  The summary is not re-prefilled; it is cached.

Mechanism, stated at the measurement level: the endpoint's reusable prefix lags the
rendered tail by 0–3 messages (1–2 turns pre-fold, 3–4 turns post-fold). A fold deepens the
lag from ~1 turn to ~3, which is why the post-fold re-prefill is 4× the pre-fold one
(288 → 1,172) even though no carried node changed.

## Result — F's turns 36–40 (same cause, different depth)

F reproduces U15's F to the token when the arm has a full warm epoch (`F2`, salt 2503):
t35–38 `cached` 768/2048/2048/2944 = U15's F exactly, `uncached` 455/919/450 vs U15's
458/922/453. F2 t36–38 mean uncached 608 = 444 new tail + 14 boundary + **149 re-prefill**
(lag 1 turn), against R's t36–40 1,587 = 459 + 40 + **1,088** (lag 3 turns). So F's
advantage is the same *component* — tail re-prefill — with a shorter reuse lag.

**But a warm epoch is necessary for this comparison, and the arm still contributes (an
interaction) which this design does not isolate.** The same F arm run live only from turn 30
(`E2F`, cold epoch entry, cached 0 at t30) carried R-*magnitude* re-prefill, not R's reuse cuts:
t36–38 `cached` 768/768/2048, `uncached` 1,735/2,199/1,346. U15's F advantage therefore needs
U15's producing order (a warm epoch from t1); the cold-F run is run-order sensitivity, not a
refutation of the arm effect.
