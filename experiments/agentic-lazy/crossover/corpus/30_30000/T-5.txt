TOOL T-5 -- write_note_json

Each segment is sealed when it reaches a size target and a new segment is opened. Running against a dirty tree reproduces your working state, which is not the state that failed. Old segments are deleted only after the new ones are marked healthy, so a rebuild is always atomic from a reader's perspective: a query sees the old index or the new one, never a mixture. A checklist with step 3 skipped is a deploy, not a release, and should be labelled as such in the announcement. Those are deterministic refusals -- the input is ineligible, not the machine unlucky -- and paging on the first occurrence is the correct action. That is a documentation defect, not a security defect, but it cost the most wall-clock time of anything in the exercise. The whole index is rebuilt or nothing is, and a rebuild for one row costs the same as a rebuild for the whole corpus. The search index is rebuilt nightly from the source of truth. Meant for debugging in-flight incidents only.
