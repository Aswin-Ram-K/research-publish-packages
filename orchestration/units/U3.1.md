# U3.1 — Paced, resilient SearXNG search client with honest failure reporting

**Status:** done · **Bound:** 32 tool calls, ≤12 real SearXNG queries · **Writable:** `src/resextract/web/__init__.py`,
`src/resextract/web/search.py`, `tests/test_web_search.py`, `state/logs/U3.1*`, `orchestration/units/U3.1.md`,

## Purpose (one)

Give the pipeline a SearXNG client that cannot silently convert "SearXNG stopped answering" into
"the literature does not exist" — and that says so loudly, in the outcome object, when it happens.

The failure mode this unit exists to fix, verbatim from the project's own research log:

> `local_web_search` (local SearXNG) — "Worked for the first ~6 queries, then returned **'no results'**
> for every subsequent query — intermittent to broken. Treat discovery as unreliable."

### Semantics that had to be right

| Concern | Implementation |
|---|---|
| `ok` vs. emptiness | `ok` = the HTTP call succeeded. `ok=True, results=[]` is "nothing found"; `ok=False` is "we could not ask". Never conflated. |
| Pacing | One shared limiter (`threading.Lock` + monotonic ts) enforces `min_interval_s ± jitter` between **any** two requests, including engine retries and 429 retries. |
| Engine rotation | On `ok=True` with zero results, retry the next engine, up to `max_attempts`. Default set `google, duckduckgo, bing, arxiv`. |
| 429 | Honour `Retry-After` (seconds or HTTP-date); otherwise exponential backoff + jitter; recorded as a **failed** attempt; backoff via the injected `sleep`. |
| Negative cache | Keyed `(query, engine-set)`. Zero-result queries expire after `negative_ttl_s`; `force=True` or a different engine set bypasses. A cache hit makes zero HTTP requests. |
| Degradation | Consecutive **distinct** zero-result queries are counted. On the 3rd, `degraded` latches for the client's lifetime; every later empty outcome carries a note naming the triggering queries and telling downstream code to mark prior art `UNVERIFIED`. |
| Honesty | Transport failures never populate the negative cache (that would launder an outage into a finding). |

## Live evidence (≤12 real queries, paced)

Field-probe curl on `sandboxing LLM agents survey` (1 query) + 11 client queries = **12 real queries**.
Probe settings: `min_interval_s=1.5, jitter_s=0.5, max_attempts=1` (one HTTP request per query — keeps the
shared box quiet and the budget exact), engines rotated manually one per query.

- 7 distinct research queries: **5 with results (10 hits each), 2 empty, 0 errors**, latencies
  **172–948 ms**; 0 latency 469 ms. Degradation did **not** latch (real results were interleaved).
- **Rapid probe: 4 identical forced queries → 4/4 empty**, every one `ok=True`, latencies **2.0–2.6 ms**.
- The two empties on the distinct pass: `capability-based security agent isolation` (google, 469 ms) and
  `retrieval nDCG hybrid BM25 evaluation` (google, **6.7 ms**).
- **Signature finding:** genuinely-answered requests take 172–948 ms; the zero-result responses take
  2–7 ms — an empty page from this SearXNG returns *faster than any real search could run*, and
  `unresponsive_engines` stays `[]`, so the service does **not** admit the failure. Latency is therefore
  a usable second degradation signal for the next unit.
- Observed raw field names (result objects): `title`, `url`, **`content`** (the snippet),
  **`publishedDate`** (and also `pubdate`), `engine`, `engines`, `score`, `parsed_url`, `category`,
  `thumbnail`, `img_src`, `template`, `positions`, `priority`. Envelope:
  `query, results, answers, corrections, infoboxes, suggestions, unresponsive_engines`.
