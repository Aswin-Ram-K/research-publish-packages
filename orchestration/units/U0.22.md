## ITEM 1 — slow vs down
**Reproduction (before the fix).** A local `ThreadingHTTPServer` on `127.0.0.1:18777` that accepts and sleeps 6.0 s (bound 5.0), started/probed/killed inside one bash call (teardown proven by `connect_ex == 111`):
`SearXNG -> ReadTimeout: timed out (5.044 s)`, `ok=false`, **in `core_down`**, `core_down == ['Occamy','SearXNG']`, **exit 2** → `state/logs/U0.22-before.json`.
Live SearXNG (real-world instance): 6/6 HTTP 200, samples `1.2399, 0.7644, 1.3868, 0.7385, 1.9784, 0.968` s → min/median/max **0.7385 / 1.1040 / 1.9784**; a fresh probe during the after-run took **3.536 s**, still up. V0.21's 8.232 s max shows a live sample can exceed the bound.
**After.** `state=slow`, `core_down == []`, `core_slow == ['SearXNG']`, `exit 0`, `degraded true`; table prints `slow` and `CORE SLOW: SearXNG`.

**Design.** On the timeout path only, the doctor runs a cheap TCP-connect liveness check (`SLOW_LIVENESS_TIMEOUT = 0.5 s`) against the leg's host:port (the four HTTP legs; `graphify` is a subprocess with no host:port and stays DOWN).
- `slow` = the full probe exceeded its bound **but something is still accepting** on that host:port; reachable, not proven green (`ok` stays false), never called UP.
- **Not** in `core_down`; **does not** affect the exit code (a slow core leg changes neither 0/2 nor `ok`, whose documented meaning is DOWN-only). Justification: reporting a reachable dependency DOWN is the defect; and `tests/test_cli.py:281-283` (another unit's file, not editable here) pins `code == 0 iff core_down == []` and `ok == (code == 0)`, so a third exit code would make a live SearXNG flakily fail that sibling test — a bound manufacturing a failure again.
- **Where a caller sees it:** per-leg `state="slow"` (`slow=true`, `bound_s`), new `core_slow`/`optional_slow`, `degraded=true`, and the table. `only DOWN is remembered`: `finish()` never caches a slow verdict.
- **Bound unchanged: 5.0 s** (pinned by a new assertion).

## Residual
